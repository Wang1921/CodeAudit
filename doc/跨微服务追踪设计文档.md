# 跨微服务追踪设计文档
**版本**: V2.1  |  **所属子系统**: 跨微服务追踪机制

## 1. 设计目标

实现跨微服务的漏洞追踪，解决以下问题：
- 自动识别项目中的微服务结构（通过扫描子目录）
- 支持跨服务调用链追踪
- 引擎直接发现微服务（`engine._discover_microservices()`），无需独立调度 Agent
- **按 `(protocol, target_identifier)` 去重，多个 sink 命中同一跨服务目标时只追踪一次**

## 2. 核心架构

```
┌─────────────────────────────────────────────────────┐
│           ReverseTracer                      │
│      (processor-service)                       │
│           ↓ 发现微服务边界                     │
│  输出: CrossServiceTraceRequest                │
└─────────────────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────────────────┐
│         Engine._handle_cross_service...          │
│                                              │
│  1. 扫描子目录发现微服务                    │
│  2. 并发启动 Relay ReverseTracer             │
└─────────────────────────────────────────────────────┘
                    ↓
    ┌────────────────────┴────────────────────┐
    ↓                                         ↓
┌─────────────────────┐              ┌─────────────────────┐
│  Relay ReverseTracer │              │  Relay ReverseTracer │
│   (user-service)    │              │  (processor-service)│
└─────────────────────┘              └─────────────────────┘
```

## 3. 追踪流程

### 3.1 边界发现
1. ReverseTracer 在溯源时遇到微服务边界
2. 边界类型：
   - `@KafkaListener` 消费消息
   - `RestTemplate` HTTP 调用
   - `@FeignClient` 声明式调用
3. 输出 `CrossServiceTraceRequest` 消息

### 3.2 引擎接管 + 去重缓存
1. 引擎检测到 `CrossServiceTraceRequest` 消息类型，提取 `(protocol, target_identifier)` 作为缓存键。
2. **In-flight coalescing**：在 `_cross_service_cache` 中查找同 key 的 `asyncio.Future`：
   - 不存在 → 本请求成为 owner，创建 Future 并真实发起追踪。
   - 已存在 → 本请求是 follower，直接 `await` 该 Future，复用 owner 的结果。
3. owner 通过 `service_route_map`（或回退扫描子目录）确定全部微服务。
4. owner 异常时清出缓存，允许后续请求重试。

### 3.3 并发追踪（owner 路径）
1. 在每个微服务中并发启动接力 ReverseTracer，`asyncio.gather(return_exceptions=True)` 收敛。
2. `_run_relay_agent` 返回 `parsed_result`（贯通成功）或 `None`（NOT_EXPLOITABLE / 无链路）。
3. 收集为 `Dict[service_name, parsed_result|None]` 写入 Future。

### 3.4 结果派发（owner 与 follower 共用）
1. 遍历 Future 中的命中结果，按本请求的 `task_id` 派发 `VulnCandidate` → `RedValidator`。
2. 同一目标被 N 个 sink 触发时：N 次派发都取同一份 LLM 计算结果，但每次都生成独立的红蓝对抗链路（task_id 不同），保留各 sink 的上下文。
3. 标记原 `CrossServiceTraceRequest` 为 completed，`agent_result` 内含 `cache_hit`、`hits`、`services_searched`。

## 4. 消息格式

### 4.1 跨服务追踪请求 (CrossServiceTraceRequest)

**用途**：由 ReverseTracer 发出，引擎接管后在所有微服务中并发拉起接力 ReverseTracer。

| 字段名 | 数据类型 | 必填 | 描述 |
| :--- | :--- | :--- | :--- |
| `action` | String | 是 | 固定值 "cross_service_trace" |
| `vuln_type` | String | 是 | 漏洞类型 |
| `protocol` | String | 是 | 通信协议（HTTP/KAFKA/MQ） |
| `target_identifier` | String | 是 | 目标标识符（如 Topic 名称或 URL 路径） |
| `historical_chain` | Array[String] | 是 | 历史调用链 |
| `taint_variable` | String | 是 | 污点变量名 |

**JSON 示例**：
```json
{
  "action": "cross_service_trace",
  "vuln_type": "SpEL Injection",
  "protocol": "KAFKA",
  "target_identifier": "eval-requests",
  "historical_chain": [
    "1. 当前服务: KafkaConsumerService.handleEvalRequest() 监听 Kafka topic 'eval-requests'",
    "2. 当前服务边界入口: @KafkaListener(topics = \"eval-requests\") 从 Kafka 消息获取 request.getExpression()",
    "3. 当前服务: evalService.evaluate(expression) 传入下游 SpEL 解析"
  ],
  "taint_variable": "request.getExpression()"
}
```

### 4.2 接力 Payload

**用途**：引擎构建的传递给 Relay ReverseTracer 的 Payload。

**关键特性**：
- 保留原始 `sink_details` 的所有字段
- 保留 `historical_chain` 作为历史参考
- 添加 `cross_service_info` 包含协议和目标标识符
- 仅在原始 `filepath` 不存在时使用 `${protocol}://${target_id}` 作为回退

**JSON 示例**：
```json
{
  "action": "trace_call_chain",
  "sink_details": {
    "vuln_class": "home.semgrep-rules.java.spring.security.audit.spel-injection",
    "filepath": "/home/CodeAudit/.../EvalServiceImpl.java",
    "line_number": 10,
    "end_line": 14,
    "column": 5,
    "end_column": 6,
    "dangerous_code": "String expression = parser.parseExpression(request.getExpression())",
    "taint_variable": "request.getExpression()",
    "cwe": ["CWE-94"],
    "check_id": "home.semgrep-rules.java.spring.security.audit.spel-injection",
    "severity": "WARNING"
  },
  "historical_chain": [
    "1. 当前服务: KafkaConsumerService.handleEvalRequest() 监听 Kafka topic 'eval-requests'"
  ],
  "cross_service_info": {
    "protocol": "KAFKA",
    "target_identifier": "eval-requests"
  }
}
```

## 5. 微服务识别

### 5.1 识别方式

引擎在启动时直接扫描目标目录的第一层子目录：

```python
def _discover_microservices(self) -> dict:
    """扫描目标目录的第一层子目录，发现微服务"""
    service_map = {}
    root_path = Path(self.target_source_dir)
    
    for entry in root_path.iterdir():
        if entry.is_dir() and not entry.name.startswith('.'):
            service_map[entry.name] = str(entry)
    
    return service_map
```

### 5.2 构建文件检测（回退逻辑）

当无法从 service_route_map 找到对应目录时，引擎会逐级向上查找构建文件：

- `pom.xml` (Maven)
- `package.json` (Node.js)
- `go.mod` (Go)
- `build.gradle` (Gradle)

## 6. 全局服务路由表

### 6.1 构建时机

引擎启动时（is_fresh_start），自动扫描子目录构建：

```python
if is_fresh_start:
    # 发现微服务
    self.service_route_map = self._discover_microservices()
    
    # 直接调用 Semgrep 扫描
    scanner = SemgrepScanner(self.target_source_dir, rules_path=self.semgrep_rules)
    scan_result = scanner.scan()
    
    # 分发扫描结果
    self._dispatch_scan_results("TASK-INIT-001", scan_result)
```

### 6.2 数据结构

```python
service_route_map = {
    "user-service": "/path/to/user-service",
    "processor-service": "/path/to/processor-service"
}
```

## 8. 结果处理

### 8.1 成功接力

如果 Relay ReverseTracer 成功找到外网入口：

```python
if parsed_result.get("status") != "NOT_EXPLOITABLE":
    logging.info(f"微服务 [{service_name}] 成功接力并贯通外网入口！")
    self.tracker.add_task()
    self.bus.write_message(
        message_type="VulnCandidate",
        task_id=f"{base_task_id}_HIT_{service_name}",
        sender="ReverseTracer",
        recipient="RedValidator",
        payload=parsed_result
    )
```

### 8.2 失败处理

如果 Relay ReverseTracer 未发现调用链：

```python
else:
    logging.debug(f"微服务 [{service_name}] 中未发现调用链路。")
```

## 9. 关键特性

### 9.1 原始上下文保留
- 保留原始 `sink_details` 的所有字段
- 保留 `historical_chain` 作为历史参考
- 添加 `cross_service_info` 包含协议和目标信息

### 9.2 动态工作目录推断
- 优先从 `service_route_map` 查找
- 回退到启发式逻辑
- 确保 Agent 在正确的微服务目录中运行

### 9.3 并发执行
- 在所有微服务中并发启动
- 使用 `asyncio.create_task` 异步执行
- 不阻塞主线程

### 9.4 容错处理
- 单个微服务失败不影响其他
- 自动记录错误日志
- 确保系统稳定性

## 10. 优化建议

### 10.1 性能优化
- 限制并发微服务数量
- 使用缓存减少重复扫描

- 显示服务路由表

### 10.3 可扩展性
