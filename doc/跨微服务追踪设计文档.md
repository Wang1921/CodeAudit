# 跨微服务追踪设计文档
**版本**: V1.0  |  **所属子系统**: 跨微服务追踪机制

## 1. 设计目标

实现跨微服务的漏洞追踪，解决以下问题：
- 自动识别项目中的微服务结构
- 支持跨服务调用链追踪
- 构建全局服务路由表

## 2. 核心架构

```
┌─────────────────────────────────────────────────────┐
│           ReverseTracer                      │
│      (processor-service)                       │
│           ↓ 发现微服务边界                     │
│  输出: CrossServiceTraceRequest                │
└─────────────────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────────────────┐
│         Engine._handle_cross_service...          │
│                                              │
│  1. 识别所有微服务                          │
│  2. 构建跨服务追踪策略                       │
│  3. 并发启动 ReverseTracer                    │
└─────────────────────────────────────────────────────┘
                    ↓
    ┌────────────────────┴────────────────────┐
    ↓                                         ↓
┌─────────────────────┐              ┌─────────────────────┐
│  Relay ReverseTracer │              │  Relay ReverseTracer │
│   (user-service)    │              │  (processor-service)│
└─────────────────────┘              └─────────────────────┘
```

## 3. 追踪流程

### 3.1 边界发现
1. ReverseTracer 在溯源时遇到微服务边界
2. 边界类型：
   - `@KafkaListener` 消费消息
   - `RestTemplate` HTTP 调用
   - `@FeignClient` 声明式调用
3. 输出 `CrossServiceTraceRequest` 消息

### 3.2 引擎接管
1. 引擎检测到 `CrossServiceTraceRequest` 消息类型
2. 自动识别所有微服务目录
3. 构建跨服务追踪策略

### 3.3 并发追踪
1. 在每个微服务中并发启动 ReverseTracer
2. 搜索目标服务调用点
3. 逆向追踪到外部可控入口
4. 汇总结果进入红蓝对抗流程

## 4. 消息格式

### 4.1 跨服务追踪请求 (CrossServiceTraceRequest)

**用途**：由 ReverseTracer 发出，引擎接管后在所有微服务中并发拉起接力 ReverseTracer。

| 字段名 | 数据类型 | 必填 | 描述 |
| :--- | :--- | :--- | :--- |
| `action` | String | 是 | 固定值 "cross_service_trace" |
| `vuln_type` | String | 是 | 漏洞类型 |
| `protocol` | String | 是 | 通信协议（HTTP/KAFKA/MQ） |
| `target_identifier` | String | 是 | 目标标识符（如 Topic 名称或 URL 路径） |
| `historical_chain` | Array[String] | 是 | 历史调用链 |
| `taint_variable` | String | 是 | 污点变量名 |

**JSON 示例**：
```json
{
  "action": "cross_service_trace",
  "vuln_type": "SpEL Injection",
  "protocol": "KAFKA/MQ",
  "target_identifier": "eval-requests",
  "historical_chain": [
    "1. 当前服务: KafkaConsumerService.handleEvalRequest(EvalRequest request) @KafkaListener(topics = eval-requests)",
    "2. 当前服务边界入口: request.getExpression() -> evalService.evaluate(expression)",
    "3. 污点汇点: EvalServiceImpl.evaluate(String expression) - SpEL Injection at line 10-14"
  ],
  "taint_variable": "request.getExpression()"
}
```

### 4.2 接力 Payload

**用途**：引擎构建的传递给 Relay ReverseTracer 的 Payload。

**关键特性**：
- 保留原始 `sink_details` 的所有字段
- 保留原始 `tracing_strategy`
- 仅在原始 `filepath` 不存在时使用 "Cross-Boundary Discovery" 作为回退

**JSON 示例**：
```json
{
  "action": "trace_call_chain",
  "sink_details": {
    "vuln_class": "home.semgrep-rules.java.spring.security.audit.spel-injection",
    "filepath": "/home/CodeAudit/.../EvalServiceImpl.java",
    "line_number": 10,
    "end_line": 14,
    "column": 5,
    "end_column": 6,
    "dangerous_code": "String expression = parser.parseExpression(request.getExpression())",
    "taint_variable": "potentially_controlled_input",
    "cwe": ["CWE-94: Improper Control of Generation of Code ('Code Injection')"],
    "check_id": "home.semgrep-rules.java.spring.security.audit.spel-injection",
    "severity": "WARNING",
    "message": "",
    "message": ""
  },
  "tracing_strategy": "在SpringSpring Boot框架中进行动态追踪时，应遵循以下策略..."
}
```

## 5. 微服务识别

### 5.1 识别方式

**优先级 1**：从 Coordinator 建立的 `service_route_map` 查找
```python
if self.service_route_map:
    service_dirs = [Path(d) for d in self.service_route_map.values()]
```

**优先级 2**：枚举根目录一级子目录
```python
root_path = Path(self.target_source_dir)
service_dirs = [d for d in root_path.iterdir() if d.is_dir() and not d.name.startswith('.')]
```

### 5.2 构建文件检测

通过以下构建文件识别微服务：
- `pom.xml` (Maven)
- `package.json` (Node.js)
- `go.mod` (Go)
- `build.gradle` (Gradle)

## 6. 全局服务路由表

### 6.1 构建时机
- Coordinator 完成后自动构建
- 根据 `rpc_providers` 注册

### 6.2 数据结构

```python
service_route_map = {
    "user-service": "/path/to/user-service",
    "processor-service": "/path/to/processor-service"
}
```

### 6.3 使用场景
- 动态推断 Agent 工作目录
- 跨服务追踪时识别微服务
- 生成完整的服务调用图

## 7. 动态追踪策略构建

### 7.1 策略模板

```python
cross_tracing_strategy = (
    f"【最高优先级跨界任务】: 你的前序特工在另一个微服务发现了漏洞，"
    f"你需要接力追踪！请全局搜索当前代码库，找到所有向 {protocol} 目标 `{target_id}` "
    f"发起请求或发送消息的代码点（如 RestTemplate.postForObject('{target_id}') 或 kafkaTemplate.send('{target_id}')）。"
    f"以这些发送点为 Sink 坐标，继续向上逆向追踪到当前微服务的外部可控 API 入口！\n"
    f"【历史调用链参考】: {json.dumps(payload.get('historical_chain', []), ensure_ascii=False)}"
)
```

### 7.2 策略注入

通过 `_get_prompt_for_agent` 方法注入：
```python
prompt = self._get_prompt_for_agent(
    "ReverseTracer",
    json.dumps(relay_payload, ensure_ascii=False),
    {"dynamic_tracing_strategy": cross_tracing_strategy}
)
```

## 8. 结果处理

### 8.1 成功接力

如果 Relay ReverseTracer 成功找到外网入口：
```python
if result.get("status") != "NOT_EXPLOITABLE":
    self.tracker.add_task()
    self.bus.write_message(
        message_type="VulnCandidate",
        task_id=f"{base_task_id}_HIT_{service_name}",
        sender="ReverseTracer",
        recipient="RedValidator",
        payload=result
    )
```

### 8.2 失败处理

如果 Relay ReverseTracer 未发现调用链：
```python
else:
    logging.debug(f"微服务 [{service_name}] 中未发现调用链路。")
```

## 9. 关键特性

### 9.1 原始上下文保留
- 保留原始 `sink_details` 的所有字段
- 保留原始 `tracing_strategy`
- 确保后续 Agent 能获取完整信息

### 9.2 动态工作目录推断
- 优先从 `service_route_map` 查找
- 回退到启发式逻辑
- 确保 Agent 在正确的微服务目录中运行

### 9.3 并发执行
- 在所有微服务中并发启动
- 使用 `asyncio.create_task` 异步执行
- 不阻塞主线程

### 9.4 容错处理
- 单个微服务失败不影响其他
- 自动记录错误日志
- 确保系统稳定性
