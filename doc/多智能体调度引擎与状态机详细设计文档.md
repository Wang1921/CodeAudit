## 1. 引擎定位与核心职责 (Engine Overview)

调度引擎（Orchestrator）是整个双轨对抗式审计系统的"心脏"。它本身不直接执行代码审计逻辑，而是作为一个**基于本地文件系统的事件驱动型守护进程 (Event-Driven Daemon)** 运行。

**核心职责包括**：
1. **总线监听与分发**：轮询 `.a2a_bus/pending/` 目录，解析 A2A JSON 信封
2. **进程生命周期管理**：通过 Claude Agent 会话管理器安全地拉起、监控、并回收 Claude Code CLI 子进程
3. **并发控制 (Fan-out/Fan-in)**：处理任务的裂变与并行调度，最大化利用 Claude Code 的并发额度
4. **容错与重试 (Fault Tolerance)**：处理大模型输出乱码、进程死锁或超时等异常边界情况
5. **Semgrep 扫描集成**：引擎启动时直接触发 Semgrep 扫描，一次性获取 API 路由和漏洞点
6. **跨微服务追踪支持**：处理跨微服务追踪求救信号，在所有微服务中并发启动溯源 Agent
7. **报告生成与去重**：收尾时生成 SUMMARY.md，按 (vuln_type, entry_route, location.file) 去重

## 2. 并发与异步执行模型 (Concurrency Model)

为了解决海量文件扫描和多路由并行推演的性能瓶颈，引擎全面采用 **Python `asyncio` 异步非阻塞模型**。

### 2.1 异步会话管理
+ **工作流**：当引擎读取到一个 TaskRequest 时，它会创建一个异步 Task，挂起等待 Claude Agent 执行完毕，同时主线程继续去 `.a2a_bus/` 拾取下一个任务。
+ **并发池管控 (Semaphore)**：引擎全局维护 `asyncio.Semaphore(MAX_CONCURRENT_AGENTS)` 限制最高并发数（默认 5）。
+ **动态扩容**：引擎在 `_discover_microservices()` 后上调至 `max(5, 服务数)`。

### 2.2 Claude Agent 会话管理
+ **会话管理器**：`ClaudeAgentManager` 类管理多个 Claude Code CLI 会话。
+ **容量与项目规模匹配**：默认 `max_active=5`；引擎启动时按微服务数自动扩容。
+ **细粒度锁**：不同 `cwd` 的冷启动并行，同 `cwd` 的热路径查询无全局串行。
+ **双回收策略**：LRU（容量满时淘汰最旧）+ Session 空闲监控（默认 60 秒空闲回收）。

### 2.3 任务隔离与工作目录挂载 (cwd)
+ 所有的 Agent 进程在拉起时，工作目录锁定在被审计的微服务子目录下。
+ 依据文件路径归属动态推断工作目录（根目录 vs 微服务子目录）。

## 3. Semgrep 静态扫描集成 (Semgrep Integration)

### 3.1 扫描触发时机
+ 引擎启动时（is_fresh_start），自动触发 Semgrep 扫描。
+ 一次性获取 API 路由和漏洞点，提高扫描效率。

### 3.2 扫描结果处理
+ **路由结果**：为每个 API 路由生成 LogicAuditor 任务。
+ **漏洞点结果（按 `taint_required` 分流）**：
  + `taint_required: true`（默认，注入类 / 反序列化 / SSRF / XXE 等需要证明 source→sink 连通性的漏洞）
    → 派发 **ReverseTracer** 任务，走完整污点链（ReverseTracer → RedValidator → BlueValidator → 报告落盘）。
  + `taint_required: false`（弱加密 / 弱随机 / 硬编码凭证等"sink 即漏洞"、无须用户输入的静态定性场景）
    → 走 **fast path** 直接派发 **ConfigValidator** 任务（跳过 ReverseTracer 与 RedValidator）。
+ **规则侧契约**：Semgrep 规则通过 `metadata.taint_required: false` 标记 fast path。
+ **去重**：无论哪条路径，入口先按 `(vuln_class, filepath, line_number)` 去重。

## 4. 状态机与任务路由流转 (State Machine & Routing)

引擎通过数据驱动的 `ROUTE_RULES: Dict[str, RouteRule]` 来决定任务完成后应该交给谁（见 `src/state_router.py`）。

### 4.1 核心路由表定义

| 发送方 (Sender) | 消息类型 (MessageType) | 触发条件 | 下一跳接收方 (Recipient) | 操作动作 (Action) |
| :--- | :--- | :--- | :--- | :--- |
| `System` | `TaskRequest` | 引擎首次启动 | 直接触发 Semgrep 扫描 | 扫描路由+漏洞点 |
| `SemgrepScanner` | `TaskRequest` | 扫描完成（route）| `LogicAuditor` (按路由并行) | 路由裂变 |
| `SemgrepScanner` | `TaskRequest` | 扫描完成（sink，`taint_required:true`）| `ReverseTracer` (按漏洞点并行) | 完整污点链入口 |
| `SemgrepScanner` | `TaskRequest` | 扫描完成（sink，`taint_required:false`）| `ConfigValidator` (按漏洞点并行) | **fast path**: 跳过反向追踪与红队 |
| `ReverseTracer` | `VulnCandidate` | 连通性确认完毕 | `RedValidator` | 提交给红队进行攻击推演 |
| `ReverseTracer` | `CrossServiceTraceRequest` | 遇到微服务边界 | `Orchestrator` (引擎处理) | 触发跨微服务追踪 |
| `LogicAuditor` | `VulnCandidate` | 发现业务逻辑缺陷 | `RedValidator` | 提交给红队进行攻击推演 |
| `LogicAuditor` | `VulnCandidate` | 遇到技术类漏洞 | — | 直接丢弃，让位 Sink 路径 |
| `RedValidator` | `ExploitAttempt` | 成功构造 POC | `BlueValidator` | 提交给蓝队进行防御核查 |
| `BlueValidator` | `ConfirmedVuln` | 防御被击穿 | `Report` | 写入漏洞报告队列 |
| `ConfigValidator` | `ConfirmedVuln` | 静态定性确认 | `Report` | 写入漏洞报告队列 |

### 4.2 终止状态 (Terminal States)

引擎在解析 JSON 后，若检测到以下特殊 `status` 字段，将**立即终止该任务链路**：

1. `NOT_EXPLOITABLE`: ReverseTracer/RedValidator 判定参数写死或无利用价值
2. `DEFENDED`: BlueValidator/ConfigValidator 确认代码中存在有效的防御机制

## 5. 跨微服务追踪机制 (Cross-Service Tracing)

### 5.1 微服务发现
+ 严格模式：只有**根目录无构建文件且子目录各自有 `pom.xml` / `build.gradle` / `package.json` / `go.mod` 等**才识别为多微服务
+ 避免 BenchmarkJava 这类单项目下的普通子目录被误识别

### 5.2 追踪触发
+ ReverseTracer 在溯源时遇到微服务边界（如 `@KafkaListener` 或 `RestTemplate` / `@FeignClient` 调用）
+ 输出 `CrossServiceTraceRequest` 消息

### 5.3 引擎接管
+ 引擎检测到 `action: cross_service_trace` 消息
+ 自动使用已构建的服务路由表，在每个微服务中并发启动 ReverseTracer

### 5.4 Echo 污染检测
+ LLM 输出 `action=cross_service_trace` 但同时含 `call_chain` / `entry_route` 时清洗场景 B 字段后按场景 A 派发
+ 避免 fan-out 风暴

---

## 6. vuln_type 全链路强制规范化

+ `vuln_type` 是漏洞聚合 / CWE 映射 / 报告分类的唯一 key
+ `state_router._build_merged_payload` 在每次跨 Agent merge 时把 `vuln_type` 强制还原到上游权威值（`sink_details.vuln_class`）
+ 即使 LLM 偶发写成 "CWE-918: ..." 或 "服务端请求伪造" 也会被自动覆盖

---

## 7. 报告生成与去重 (Report Generation & Deduplication)

### 7.1 报告落盘
+ 每个 VULNERABLE 漏洞落盘为 `<target_dir>/reports/vulnerability_<task_id>_<timestamp>.json`
+ 纯 Python 字段映射，无 LLM

### 7.2 报告层去重
+ 按 `(vuln_type, entry_route, location.file)` 聚合
+ 同一漏洞类型 + 同一入口路由 + 同一 sink 文件路径只保留一条
+ 保留严重度最高的

### 7.3 SUMMARY 汇总
+ 引擎收尾自动生成 `<target_dir>/reports/SUMMARY.md`
+ 按严重度排序，含按类型 / 按文件 Top10 / 失败任务统计

---

## 8. 容错、超时与死信机制 (Fault Tolerance)

### 8.1 契约破坏处理 (JSON Contract Enforcement)

+ **第一层 · 服务端 JSON Schema 强校验**：Claude Agent SDK 的 `output_format` 指定 JSON Schema，服务端返回结构化输出并自动校验
+ **第二层 · 客户端轻量降级**：若 `structured_output` 缺失，`state_router._extract_parsed` 会回退到 response 文本提取 JSON
+ **第三层 · 死信兜底**：所有解析失败的任务在看板标记 `DEFENDED`，协程异常则移入 `.a2a_bus/failed/`

### 8.2 超时控制

| Agent | 默认超时 |
|-------|----------|
| LogicAuditor | 480s（跨文件追读耗时长）|
| 其他 Agent | 300s |

### 8.3 文件系统操作的原子性

+ **读取策略**：使用 `os.rename(src, temp_processing_dir)` 将任务文件原子的移动到"处理中"状态区
+ **写入策略**：先写入 `.tmp` 后缀的文件，写入并 `fsync` 刷盘完成后，再原子重命名为 `.json`

---

## 9. 核心类结构抽象 (Class Architecture)

1. `A2ABusManager`: 负责底层文件系统的原子读写、目录初始化、以及归档 (`completed/`, `failed/`) 管理
2. `ClaudeAgentManager`: 负责管理多个 Claude Code CLI 会话，采用 LRU 缓存策略，支持空闲回收
3. `ClaudeAgent`: 负责封装 Claude Agent SDK 客户端，处理会话创建、消息发送、删除
4. `StateRouter`: 负责根据路由表，解析上游的 Payload，生成下一跳的 A2A JSON 文件
5. `StateTracker`: 负责 Web 前端状态追踪，维护 Agent 状态、Token 消耗、任务进度等；漏洞数据从 target_dir/reports/ 读取
6. `SemgrepScanner`: 负责 Semgrep 静态扫描，将输出转换为标准格式
7. `AuditEngine`: 主循环 (Event Loop) 的控制者，维护 `asyncio.Semaphore` 限制并发，协调上述模块持续运作

## 10. 引擎启动与退出流程

```
1. 初始化组件
   ├── A2ABusManager
   ├── StateRouter
   ├── StateTracker
   └── ClaudeAgentManager(max_active=5)

2. 检查是否为首次启动 (is_fresh_start)
   └── 如果是：
       ├── 扫描子目录发现微服务 (_discover_microservices)
       ├── 构建 service_route_map
       ├── 按 max(5, len(service_route_map)) 扩容沙盒池
       ├── 调用 Semgrep 扫描 (semgrep_rules)
       ├── 解析扫描结果 (routes + sinks)
       └── 分发任务 (_dispatch_scan_results，入口去重 sinks/routes)
           ├── 为每个路由生成 LogicAuditor 任务
           └── 为每个漏洞点按 taint_required 分流：
               ├── True  (注入/反序列化/SSRF 等) → ReverseTracer → RedValidator → BlueValidator
               └── False (弱加密/弱随机/硬编码等 fast path) → ConfigValidator

3. 启动后台任务
   └── tracker_task = asyncio.create_task(_update_tracker_loop())

4. 主循环（自然退出）
   idle_ticks = 0
   while True:
       tasks = bus.get_pending_tasks()
       for filepath in tasks:
           t = asyncio.create_task(process_task(filepath))
           inflight.add(t); t.add_done_callback(inflight.discard)
       if not tasks and not inflight:
           idle_ticks += 1
           if idle_ticks >= 2:   # 连续 2 轮稳定空闲 → 退出
               break
       else:
           idle_ticks = 0
       await asyncio.sleep(1)

5. 优雅关停 (finally)
   ├── tracker_task.cancel() + await
   ├── await gather(*inflight, timeout=5s)
   └── await agent_manager.shutdown_all()

6. 报告生成
   └── build_summary(target_dir/reports/, target_dir, project_name)
       └── 按 (vuln_type, entry_route, location.file) 去重
       └── 生成 SUMMARY.md
```

**主循环退出条件的正确性**：
`process_task` 的顺序是"路由写新消息到 `pending/` → `mark_completed` → 协程结束"。
主循环先 `get_pending_tasks()` 再检查 `inflight`：
- 协程仍在跑 → `inflight` 非空 → 不退出
- 协程刚结束 → 它写的新消息已在 `pending/` → 下一轮能捡起
连续 2 轮都返空才退出，额外一次 idle buffer 兜住极端调度 race。
