# 详细设计文档：多智能体调度引擎与状态机
**版本**: V3.0  |  **所属子系统**: 核心控制面 (Control Plane)

## 1. 引擎定位与核心职责 (Engine Overview)
调度引擎（Orchestrator）是整个双轨对抗式审计系统的"心脏"。它本身不直接执行代码审计逻辑，而是作为一个**基于本地文件系统的事件驱动型守护进程 (Event-Driven Daemon)** 运行。

**核心职责包括**：
1. **总线监听与分发**：轮询 `.a2a_bus/pending/` 目录，解析 A2A JSON 信封。
2. **进程生命周期管理**：通过 HTTP 沙盒池管理器安全地拉起、监控、并回收 `opencode` CLI 子进程。
3. **并发控制 (Fan-out/Fan-in)**：处理任务的裂变（如从 1 个 Semgrep 扫描结果生成多个独立审计任务）与并行调度，最大化利用大模型 API 的并发额度。
4. **容错与重试 (Fault Tolerance)**：处理大模型输出乱码、进程死锁或超时等异常边界情况。
5. **Semgrep 扫描集成**：引擎启动时直接触发 Semgrep 扫描，一次性获取 API 路由和漏洞点。
6. **跨微服务追踪支持**：处理跨微服务追踪求救信号，在所有微服务中并发启动溯源 Agent。
7. **动态工具权限分配**：根据 Agent 角色动态分配工具权限（如 LogicAuditor、RedValidator 等 Agent 使用 lsp）。

## 2. 并发与异步执行模型 (Concurrency Model)
为了解决海量文件扫描和多路由并行推演的性能瓶颈，引擎全面采用 **Python `asyncio` 异步非阻塞模型**。

### 2.1 异步子进程管理
+ **工作流**：当引擎读取到一个 TaskRequest 时，它会创建一个异步 Task，挂起等待 `opencode` HTTP 请求完毕，同时主线程继续去 `.a2a_bus/` 拾取下一个任务。
+ **并发池管控 (Semaphore)**：为了防止一次性拉起上百个并发会话导致宿主机 OOM 或 API 触碰 Rate Limit，引擎全局维护一个 `asyncio.Semaphore(MAX_CONCURRENT_AGENTS)`，限制最高并发数（默认 20）。
+ **扇出任务追踪**：主循环把所有 `asyncio.create_task(process_task(...))` 加入 `inflight: set[Task]`，`done_callback` 自动 discard；配合 `get_pending_tasks()` 的返回值即可判定"全部稳定"并**自然退出**（见 §10）。

### 2.2 HTTP 沙盒池管理
+ **沙盒池管理器**：使用 `OpenCodeServerManager` 类管理多个 OpenCode 服务器实例，详见 `doc/HTTP沙盒池设计文档.md`。
+ **容量与项目规模匹配**：默认 `max_active_servers=5`；引擎在 `_discover_microservices()` 后上调至 `max(5, 服务数)`，避免 N>5 服务时反复 LRU 淘汰。
+ **细粒度锁**：`_dict_lock`（护字典）+ per-cwd `_startup_locks`（串行同目录冷启动）；subprocess 启动 / 健康检查 / dispose 全部在锁外执行。不同微服务的冷启动可真正并行。
+ **健康检查**：通过 `/global/health` 在锁外轮询，deadline 30s，失败立即 dispose 并重启。
+ **空闲回收**：`check_idle_servers()` 扫描 `/session/status`，所有 session 持续 `idle` 超过 `_idle_timeout`（**默认 60 秒**）记为可回收；主循环空闲时以 `force=True` 主动清理。

### 2.3 任务隔离与工作目录挂载 (cwd)
+ 所有的 Agent 进程在拉起时，通过 HTTP 沙盒池管理器获取端口，并将工作目录锁定在被审计的微服务子目录下。
+ **安全约束**：引擎需确保 `target_source_dir` 对运行进程为**只读 (Read-Only)** 权限，防止恶意 Agent 篡改源码导致后续分析链路污染。

## 3. Semgrep 静态扫描集成 (Semgrep Integration)

### 3.1 扫描触发时机
+ 引擎启动时（is_fresh_start），自动触发 Semgrep 扫描。
+ 一次性获取 API 路由和漏洞点，提高扫描效率。

### 3.2 扫描结果处理
+ **路由结果**：为每个 API 路由生成 LogicAuditor 任务。
+ **漏洞点结果（按 `taint_required` 分流）**：
  + `taint_required: true`（默认，注入类 / 反序列化 / SSRF / XXE 等需要证明 source→sink 连通性的漏洞）
    → 派发 **ReverseTracer** 任务，走完整污点链（ReverseTracer → RedValidator → BlueValidator → ReportGenerator）。
  + `taint_required: false`（弱加密 / 弱随机 / 硬编码凭证等"sink 即漏洞"、无须用户输入的静态定性场景）
    → 走 **fast path** 直接派发 **BlueValidator** 任务（跳过 ReverseTracer 与 RedValidator，仅做静态定性 + 上下文校准假阳）。
+ **规则侧契约**：Semgrep 规则通过 `metadata.taint_required: false` 标记 fast path；
  `SemgrepScanner._parse_single_result` 从 `metadata` 透传该字段到 `sink_details.taint_required`（默认 `true`）。
+ **分发侧契约**：`AuditEngine._dispatch_scan_results` 读取 `sink_details.taint_required`，按值选择接收方（`ReverseTracer` / `BlueValidator`）并设置对应的 `action` (`trace_call_chain` / `static_audit`)。
+ **去重**：无论哪条路径，入口先按 `(vuln_class, filepath, line)` 去重（`_deduplicate`），避免多条规则同行重复派发。
+ **自动分类**：SemgrepScanner 自动区分路由和漏洞点。

## 4. 状态机与任务路由流转 (State Machine & Routing)
引擎通过一个单向无环的**路由决策树 (Routing Table)** 来决定一个任务完成后，其结果应该交给谁。
自 V3.1 起，路由实现从 6 个硬编码方法重构为**数据驱动的 `ROUTE_RULES: Dict[str, RouteRule]`**
（见 `src/state_router.py`），新增/调整节点只需在表里追加一条 `RouteRule` 条目。

### 4.1 核心路由表定义
| 发送方 (Sender) | 消息类型 (MessageType) | 触发条件 | 下一跳接收方 (Recipient) | 操作动作 (Action) |
| :--- | :--- | :--- | :--- | :--- |
| `System` | `TaskRequest` | 引擎首次启动 | 直接触发 Semgrep 扫描 | 扫描路由+漏洞点 |
| `SemgrepScanner` | `TaskRequest` | 扫描完成（route）| `LogicAuditor` (按路由并行) | 路由裂变 |
| `SemgrepScanner` | `TaskRequest` | 扫描完成（sink，`taint_required:true`）| `ReverseTracer` (按漏洞点并行) | 完整污点链入口 |
| `SemgrepScanner` | `TaskRequest` | 扫描完成（sink，`taint_required:false`）| `BlueValidator` (按漏洞点并行) | **fast path**: 跳过反向追踪与红队 |
| `ReverseTracer` | `VulnCandidate` | 连通性确认完毕 | `RedValidator` | 提交给红队进行攻击推演 |
| `ReverseTracer` | `CrossServiceTraceRequest` | 遇到微服务边界 | `Orchestrator` (引擎处理) | 触发跨微服务追踪 |
| `LogicAuditor` | `VulnCandidate` | 发现业务逻辑缺陷 | `RedValidator` | 提交给红队进行攻击推演 |
| `RedValidator` | `ExploitAttempt` | 成功构造 POC | `BlueValidator` | 提交给蓝队进行防御核查 |
| `BlueValidator` | `ConfirmedVuln` | 防御被击穿 / 静态定性确认 | `ReportGenerator` | 写入最终漏洞报告队列 |
| `ReportGenerator` | （终点） | 生成漏洞报告 | — | `_save_vulnerability_report` 落盘到 `reports/` |

> fast path 进入 BlueValidator 时，payload 只带 `sink_details`（无 `attack_vector`/`poc_payload`），
> BlueValidator 的 prompt 通过 **Input Discriminator** 区分两类输入，走"路径 B：静态配置漏洞定性"分支，
> 读取 sink 周围上下文判定真假阳，输出仍用原有 `VULNERABLE/DEFENDED` 双分支 schema，直接进入 ReportGenerator。

### 4.2 `RouteRule` 字段（数据驱动）
每条规则声明：
- `success_check: Callable[parsed] -> bool`：命中判定
- `next_message_type / next_recipient`：命中时的下一跳消息与接收者（`None` 表终点）
- `success_kanban_category / success_kanban_status / success_details_fields`：命中时的看板写入
- `success_add_task`：命中时是否递增任务计数（`BlueValidator→ReportGenerator` 属同漏洞接力，不递增）
- `miss_kanban_label / miss_kanban_reason / miss_kanban_status`：未命中时的看板写入
- `on_success_hook`：命中时的额外副作用（仅 `ReportGenerator` 使用，用于报告落盘）

### 4.3 终止状态 (Terminal States)
引擎在解析 JSON 后，若检测到以下特殊 `status` 字段，将**立即终止该任务链路**，直接归档至 `completed/` 目录：
1. `NOT_EXPLOITABLE`: 红队判定参数写死或无利用价值。
2. `DEFENDED`: 蓝队确认代码中存在有效的 WAF 或 Filter 拦截。

注：若 Agent 同时返回终态 `status` **和**业务字段（`vuln_type` / `action` / `attack_vector` / `mitigation_advice` 等），
引擎以业务字段为准继续派发（防御 LLM 把终态当"备注"误加）。

## 5. 跨微服务追踪机制 (Cross-Service Tracing)

### 5.1 微服务发现
+ 引擎启动时通过 `_discover_microservices()` 扫描目标目录第一层子目录，自动发现所有微服务。
+ 直接构建 `service_route_map`（`service_name -> 绝对路径`），后续派发任务时按归属微服务定位沙盒。

### 5.2 追踪触发
+ ReverseTracer 在溯源时遇到微服务边界（如 `@KafkaListener` 或 `RestTemplate` 调用）。
+ 输出 `CrossServiceTraceRequest` 消息，包含跨服务追踪信息。

### 5.3 引擎接管
+ 引擎检测到 `CrossServiceTraceRequest` 消息类型。
+ 自动使用已构建的服务路由表，在每个微服务中并发启动 ReverseTracer 进行接力追踪。

### 5.4 Payload 构建
+ 保留原始 `sink_details` 的所有字段
+ 添加 `historical_chain` 作为历史调用链参考
+ 添加 `cross_service_info` 包含协议和目标标识符

## 6. 动态 Prompt 模板加载 (Dynamic Prompt Loading)

### 6.1 模板加载器
+ 引擎根据 Agent 类型从 `prompts/core/` 目录加载对应的 YAML 模板。
+ 支持变量替换（如 `{payload_json}`）。

### 6.2 模板注入
+ Semgrep 扫描完成后，引擎将扫描结果分发给 LogicAuditor 和 ReverseTracer。
+ 跨服务追踪时，直接将 relay_payload 注入到 ReverseTracer 的 Prompt 中。

## 7. 容错、超时与死信机制 (Fault Tolerance)
大模型的输出具有非确定性，CLI 工具也有崩溃的风险。引擎采用"服务端强校验 + 客户端轻降级 + 死信兜底"三层策略。

### 7.1 契约破坏处理 (JSON Contract Enforcement)
+ **第一层 · 服务端 JSON Schema 强校验**：`agent.execute` 把每个 Agent 的 `output_schema`
  作为 `format={type: json_schema}` 传给 OpenCode server，服务端内部生成一次
  `StructuredOutput` 工具调用并自行校验 JSON。校验通过的值由 `agent_output["structured_output"]`
  返回，成为引擎侧**权威值**。
+ **第二层 · 客户端轻量降级**：若 `structured_output` 缺失（如流式只拿到 text part），
  `state_router._extract_parsed` 会回退到 `response` 文本，依次尝试：
  1. 直接 `json.loads`
  2. 提取 Markdown 代码块（```json ... ```）
  - 失败即视为契约破坏，不再做激进的滑动扫描（V3.0 曾有 5 种启发式，现简化到 2 种）。
+ **第三层 · 死信兜底**：所有解析失败的任务在看板标记 `DEFENDED`，协程异常则
  `process_task` 在 except 分支调 `bus.mark_failed(filepath)` 将信封移入
  `.a2a_bus/failed/`，主流水线不卡死。
+ **同 session 重试**：上述降级失败时，`OpenCodeAgent._retry` 会在同一 session 内用
  `prompts/core/retry.yaml` 触发一次自修复提示（不单独计入 Agent 花名册）。

### 7.2 硬超时控制 (Hard Timeout)
逆向溯源（`ReverseTracer`）如果陷入了复杂的 AST 循环依赖，可能会永远卡住。

+ **策略**：使用 `asyncio.wait_for(process.communicate(), timeout=MAX_AGENT_TIMEOUT)`。
+ **阈值设定**：单次 Agent 执行上限设定为 **3600 秒（1小时）**。超时后，引擎向子进程发送 `SIGKILL` 强制回收资源，并将任务丢入死信队列。
+ **Semgrep 超时**：Semgrep 扫描超时设定为 **1200 秒（20分钟）**。

### 7.3 文件系统操作的原子性 (Atomic Operations)
由于引擎是异步高并发读取目录的，极易产生竞争条件（Race Condition）。

+ **读取策略**：引擎扫描 `pending/` 目录获取文件列表后，必须使用 `os.rename(src, temp_processing_dir)` 将任务文件原子的移动到"处理中"状态区。如果 `rename` 失败，说明被其他协程抢占��直接跳过。
+ **写入策略**：先写入 `.tmp` 后缀的文件，写入并 `fsync` 刷盘完成后，再原子重命名为 `.json`。确保引擎不会读取到只写入了一半的损坏信封。

## 8. 核心类结构抽象 (Class Architecture)
引擎的代码架构将围绕以下核心类展开：

1. `A2ABusManager`: 负责底层文件系统的原子读写、目录初始化、以及归档 (`completed/`, `failed/`) 管理。
2. `OpenCodeServerManager`: 负责管理多个 OpenCode 服务器实例，采用 LRU 缓存策略，支持空闲回收。
3. `OpenCodeAgent`: 负责封装 `opencode` HTTP 客户端，处理会话创建、消息发送、删除。
4. `StateRouter`: 负责根据路由表，解析上游的 Payload，生成下一跳的 A2A JSON 文件（核心业务逻辑层，处理 Fan-out 和 终止）。
5. `StateTracker`: 负责 Web 前端状态追踪，维护 Agent 状态、Token 消耗、任务进度等。
6. `SemgrepScanner`: 负责 Semgrep 静态扫描，将输出转换为标准格式。
7. `AuditEngine`: 主循环 (Event Loop) 的控制者，维护 `asyncio.Semaphore` 限制并发，协调上述模块持续运作。

## 9. 动态工具权限分配 (Dynamic Tool Permissions)

### 9.1 Agent 工具权限
+ **工具**: `lsp, read, codesearch`
+ **原因**: 所有 Agent 都需要的代码跳转和深度分析能力，开启重型武器 LSP。

### 9.2 动态工作目录推断
+ 引擎根据文件路径推断其所属的微服务根目录。
+ 优先从 `service_route_map` 中查找。
+ 回退到启发式逻辑：逐级向上查找构建文件（pom.xml, package.json, go.mod 等）。

## 10. 引擎启动与退出流程

```
1. 初始化组件
   ├── A2ABusManager
   ├── StateRouter
   ├── StateTracker
   └── OpenCodeServerManager(max_active_servers=5)

2. 检查是否为首次启动 (is_fresh_start)
   └── 如果是：
       ├── 扫描子目录发现微服务 (_discover_microservices)
       ├── 构建 service_route_map
       ├── 按 max(5, len(service_route_map)) 扩容沙盒池
       ├── 调用 Semgrep 扫描 (semgrep_rules)
       ├── 解析扫描结果 (routes + sinks)
       └── 分发任务 (_dispatch_scan_results，入口去重 sinks/routes)
           ├── 为每个路由生成 LogicAuditor 任务
           └── 为每个漏洞点按 taint_required 分流：
               ├── True  (注入/反序列化/SSRF 等) → ReverseTracer
               └── False (弱加密/弱随机/硬编码等 fast path) → BlueValidator

3. 启动后台任务
   └── tracker_task = asyncio.create_task(_update_tracker_loop())
       (引用被保留，run() finally 会 cancel+await)

4. 主循环（自然退出）
   idle_ticks = 0
   while True:
       tasks = bus.get_pending_tasks()
       for filepath in tasks:
           t = asyncio.create_task(process_task(filepath))
           inflight.add(t); t.add_done_callback(inflight.discard)
       if not tasks and not inflight:
           idle_ticks += 1
           if idle_ticks >= 2:   # 连续 2 轮稳定空闲 → 退出
               break
       else:
           idle_ticks = 0
       await asyncio.sleep(1)

5. 优雅关停 (finally)
   ├── tracker_task.cancel() + await
   ├── await gather(*inflight, timeout=5s)   (超时则 cancel 剩余)
   └── await server_manager.shutdown_all()   (并发 dispose 所有沙盒)
```

**主循环退出条件的正确性**：
`process_task` 的顺序是"路由写新消息到 `pending/` → `mark_completed` → 协程结束"。
主循环先 `get_pending_tasks()` 再检查 `inflight`：
- 协程仍在跑 → `inflight` 非空 → 不退出
- 协程刚结束 → 它写的新消息已在 `pending/` → 下一轮 `get_pending_tasks()` 能捡起
连续 2 轮都返空才退出，额外一次 idle buffer 兜住极端调度 race。
