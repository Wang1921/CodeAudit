**版本**: V14  |  **所属子系统**: 智能体认知与行为控制层

> 变更说明：
> - V7.x: ReportGenerator 节点下线，改为 `state_router._build_report_fields()` 纯 Python 字段映射
> - V8.x: ConfigValidator 从 BlueValidator 拆分，专门处理 taint_required=false 的静态配置漏洞

## 1. 规范概述 (Overview)

本规范旨在标准化 Claude Agent SDK 环境下各个专家智能体的 System Prompt 结构。

在当前架构下，所有的 Prompt 硬编码在 `prompts/core/` 目录下的 YAML 文件中。每个 YAML 文件同时携带 `system_prompt_template` 与 `output_schema`。Python 引擎在拉起 Claude Code CLI 前，会读取模板并使用 `.format()` 动态注入 `{payload_json}` 上下文。

由于大模型存在"幻觉 (Hallucination)"和"格式发散 (Format Deviation)"的天性，所有的系统提示词必须遵循 **"强角色预设 + 极简上下文 + 明确行动路径 + 绝对输出契约"** 的四段式框架设计。

## 2. 通用四段式提示词框架 (Universal Prompt Framework)

所有注入给智能体的 Prompt 必须严格按照以下四个模块进行组装：

1. **[Role & Context] 角色预设与环境**：你是谁？你现在在哪里？（必须明确指出它在被审计项目的源码根目录下）
2. **[Input Payload] 上游输入数据**：将 A2A 总线传来的 JSON 载荷解析并注入，提供当前任务的上下文
3. **[Action Guidelines] 行动指南**：明确它可以使用的工具，并给出具体的专家级思考流（CoT）
4. **[Output Contract] 绝对输出契约**：使用极其严厉的措辞，提供目标 JSON Schema，并禁止任何多余字符

### 3.1 逆向溯源专家 - ReverseTracer

**设计意图**：承接 Semgrep 提供的 sink 坐标，实现跨语言、跨配置文件的泛化溯源。

**关键特性**：
- 场景 A：成功追踪到外部可控入口
- 场景 B：遇到微服务边界，触发跨界追踪
- 场景 C：链路断裂，输出 `status: NOT_EXPLOITABLE` + `break_reason`（≥20 字符）
- **强制使用 CodeGraph 读取代码**，禁止仅凭方法名推断变量赋值来源
- **必须加载 skill**：`reverse-tracer`

```yaml
# 文件位置: prompts/core/reverse_tracer.yaml
role: "ReverseTracer"
description: "逆向溯源专家 - 具备跨微服务追踪能力"
system_prompt_template: |
  # Role: 逆向溯源专家 (ReverseTracer)
  用codegraph从危险 sink 自底向上追踪污点变量，还原完整调用链至外部可控入口。

  ## Input
  {payload_json}

  ## 前置步骤（必须先执行）
  用 `skill` 工具加载 `reverse-tracer` skill 获取完整工作流程和方法论，然后按指南执行污点追踪。

  ## 🚨 重要：必须输出 JSON
  无论是否使用 skill，执行完成后**必须**输出符合以下 JSON Schema 的结构化输出。

  ## 🚨 漏洞类型继承要求（绝对禁止修改）
  `sink_details.vuln_class` 已由 Semgrep 精确分类，必须逐字复制到输出 `vuln_type` 字段，
  不得翻译、标准化、转写或推断。该字段是下游去重、CWE 映射、报告聚合的唯一 key。

  ## 🚦 输出互斥约束
  - 三个场景严格互斥：场景 C 不得输出 vuln_type / entry_route / call_chain / action 等业务字段
  - 场景 A 不得输出 status 字段
  - 同时输出 DEFENDED 和 call_chain / entry_route 视为矛盾，下游直接丢弃

output_schema:
  type: object
  anyOf:
    - type: object
      required: [vuln_type, entry_route, filepath, line_number, call_chain, suspicion_reason]
      # 场景 A：成功追踪
    - type: object
      required: [action, vuln_type, protocol, target_identifier, taint_variable]
      # 场景 B：跨界追踪
    - type: object
      required: [status, break_reason]
      # 场景 C：断裂 NOT_EXPLOITABLE
```

### 3.2 业务逻辑推演专家 - LogicAuditor

**设计意图**：自顶向下审查指定的 API 路由，专门寻找传统正则工具无法发现的**状态机逻辑缺陷**。

**关键特性**：
- 输出限定 **7 类标准 vuln_type 白名单**
- 遇到技术类漏洞（SQL Injection / Path Traversal / XSS / SSRF / XXE / Unsafe Deserialization / Command Injection 等）强制返回 DEFENDED，让位 Sink 路径
- timeout=480s（比其他 agent 长）
- **必须加载 skill**：`logic-auditor`

```yaml
# 文件位置: prompts/core/logic_auditor.yaml
role: "LogicAuditor"
description: "业务逻辑审计专家 - 擅长 IDOR、条件竞争、Workflow Bypass 等"
```

### 3.3 红队验证官 - RedValidator

**设计意图**：剥离防御思维，强制大模型扮演纯粹的黑客，构思绕过手段。

**关键特性**：
- **逐参数判定 exploitability**：sink 多参数时只要任一参数仍可控就构成 EXPLOITABLE
- NOT_EXPLOITABLE 时**强制带 `defense_analysis` 字段**（minLength: 20）证明每个参数都被过滤
- Prompt 内置 13 类 vuln_type 的 PoC 构造提示
- **必须加载 skill**：`red-validator`

```yaml
# 文件位置: prompts/core/red_validator.yaml
role: "RedValidator"
description: "红队攻击验证专家 - 构造 Payload 验证漏洞可利用性"
```

### 3.4 蓝队验证官 - BlueValidator

**设计意图**：作为报告输出前的最后一道防线，专门用来寻找 WAF、拦截器和参数强转。

**关键特性**：
- **教学项目强约束**：禁止以"代码来自教学/演示/CTF/靶场（WebGoat / DVWA / Juice Shop / SecurityShepherd / Vulhub / OWASP Benchmark）"作为 DEFENDED 理由
- Prompt 路径 B 用于 fast-path 静态定性，含 7 类允许的 DEFENDED 证据 + 5 类禁用理由
- **必须加载 skill**：`blue-validator`

```yaml
# 文件位置: prompts/core/blue_validator.yaml
role: "BlueValidator"
description: "蓝队防御验证专家 - 审查过滤器、拦截器确认最终漏洞"
```

### 3.5 配置静态分析专家 - ConfigValidator

**设计意图**：从 BlueValidator 拆分，专门处理 **taint_required=false 的 14 种静态配置漏洞**。

**关键特性**：
- 走 fast-path 直接静态定性，跳过 ReverseTracer+RedValidator
- 处理：弱加密、弱随机、硬编码凭据、不安全 TLS、JWT None、不安全 Cookie、信任边界违反、敏感信息泄露等
- **敏感信息强制性裁决标准**：仅 6 类字段（密码、密钥、认证凭据、手机号、邮箱、会话标识）为敏感信息，命中即判 VULNERABLE
- **必须加载 skill**：`config-validator`

```yaml
# 文件位置: prompts/core/config_validator.yaml
role: "ConfigValidator"
description: "配置静态分析专家 - 处理 taint_required=false 的静态配置漏洞"
```

## 4. 技能加载机制 (Skill Loading)

所有 Agent 在执行任务前必须使用 `skill` 工具加载对应的 skill 文件：

| Agent | Skill 名称 |
|-------|-----------|
| ReverseTracer | `reverse-tracer` |
| LogicAuditor | `logic-auditor` |
| RedValidator | `red-validator` |
| BlueValidator | `blue-validator` |
| ConfigValidator | `config-validator` |

Skill 文件位于 `skill/<role>/SKILL.md`，包含完整工作流程、方法论和输出规范。

## 5. 结构化输出与强校验 (Structured Output)

+ 每个 Agent 的 `output_schema` 通过 **Claude Agent SDK 的 `output_format` 配置**指定 JSON Schema
+ 服务端返回结构化输出并自动校验
+ `ResultMessage.structured_output` 包含服务端校验通过的 JSON，引擎直接读取
+ 客户端二次校验：用 jsonschema 验证 structured_output
+ 降级处理：如果 structured_output 为空，从 response 文本提取 JSON
+ **SDK 无内置重试**：schema 验证失败时 SDK 直接返回 `structured_output=None`，由业务层处理

## 6. 防御性工程机制 (Defensive Mechanisms)

### 6.1 反幻觉控制 (Anti-Hallucination)

在所有负责找代码的 Agent Prompt 中，隐含要求：
- "**必须基于真实执行 codegraph/LSP/codesearch 返回的标准输出进行总结。禁止捏造未在控制台中出现的类名或代码行。**"

### 6.2 JSON 契约破损的自我修复 Prompt (Self-Correction Prompt)

当 Python 引擎捕获到 `json.JSONDecodeError` 时，会向 Agent 发送重试 Prompt：

```json
[系统级致命错误]：你刚才的输出破坏了 A2A 通信协议。
解析器返回错误：{error_details}

【指令】：请立即修复上述 JSON 格式错误，并**只**返回修复后的纯 JSON 对象。
```

## 7. vuln_type 全链路强制规范化

+ `vuln_type` 是漏洞聚合 / CWE 映射 / 报告分类的唯一 key
+ `state_router._build_merged_payload` 在每次跨 Agent merge 时把 `vuln_type` 强制还原到上游权威值（`sink_details.vuln_class`）
+ 即使 LLM 偶发写成 "CWE-918: ..." 或 "服务端请求伪造" 也会被自动覆盖
