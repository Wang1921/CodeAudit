# 智能调度与 Session 状态监控 — 落地状态

> **重要声明**：本文档原描述了一份"队列分组 + Session 状态监控 + 智能调度"的完整方案。
> 实际代码只采纳了其中的 **Session 状态监控** 与 **空闲服务器回收** 部分。
> 队列分组（`queues/<service>/` 子目录、`write_message(service_name=...)`、
> `_fan_out_coordinator_output`、`preferred_services` 等）**未进入主线**。
> 本文按当前 `src/` 实际代码重写。

## 1. 已落地的部分

### 1.1 Session 状态监控（`src/server_manager.py`）
- 服务器条目维护 `idle_since` 时间戳。
- `_fetch_session_statuses(port)`：调用 OpenCode 的 `/session/status` 取所有 session 状态。
- `check_idle_servers()`：进程退出 / 所有 session `type=="idle"` 持续超过
  `self._idle_timeout`（默认 60 秒）的服务器视为可回收。
- `evict_idle_servers(force=False)`：达到 `max_active_servers` 上限或显式 `force=True` 时，
  按空闲时长排序回收一台。

### 1.2 沙盒池 LRU + 健康检查（`src/server_manager.py`）
- `get_or_start_server(cwd)` 采用**细粒度锁三阶段**：短持 `_dict_lock` 查字典 →
  锁外健康检查 → `_startup_locks[cwd]` per-cwd 启动锁 + 锁外 subprocess。
  不同 cwd 的冷启动并行，同 cwd 多协程只触发一次 `create_subprocess_exec`。
- 启动后通过 `/global/health` 健康检查，失败立即 `_dispose_server_info` 清理进程（锁外）。
- 容量上限处理：`_evict_oldest_locked()`（字典锁内 pop）+ 锁外 dispose。
- 池容量引擎启动时按 `max(default, len(service_route_map))` 自动扩容（见 `engine.run()`）。

### 1.3 引擎主循环（`src/engine.py`）
- `AuditEngine.run()` 持续 `bus.get_pending_tasks()`，对每条 task `asyncio.create_task(process_task(...))`；
  扇出的 Task 入 `inflight: set[Task]`，`done_callback` 自动 discard。
- `get_pending_tasks()` 返空 **且** `inflight` 为空连续 2 轮即**自然退出**，
  `finally` 中 `gather(*inflight, timeout=5)`，超时则 cancel 剩余任务，再 `shutdown_all`。
- `process_task` 在 `Semaphore(MAX_CONCURRENT_AGENTS=20)` 内执行；通过
  `_get_service_dir(filepath)`（归一化为绝对路径 + 带分隔符前缀匹配 + 最长前缀优先）
  推断 cwd，再向 `server_manager` 申请端口。异常路径显式 `bus.mark_failed` +
  `tracker.agent_finish`，不泄漏 `processing/`。

## 3. 关键配置

```python
# src/server_manager.py
self._idle_timeout = 60.0       # 所有 session 持续 idle 超过此时长才回收
self.max_active_servers = 5     # 默认最大并发沙盒数；engine.run() 会按微服务数上调
                                # 至 max(5, len(service_route_map))
self.health_check_timeout = 30  # 启动健康检查超时
```

```python
# src/engine.py
MAX_CONCURRENT_AGENTS = 20      # process_task 同时在跑的上限
MAX_AGENT_TIMEOUT = 3600        # 单个 LLM agent 调用超时
```

## 4. 未来可继续探索

仍然值得做的方向（已从原方案蒸馏）：

1. **按微服务分组队列** — 同 cwd 任务连续执行可显著减少沙盒切换；细粒度锁 + 池自扩容
   已大幅缓解冷启动瓶颈，但交叉仍有非零概率触发 `evict + start`。
2. ~~**基于服务规模的动态 `max_active_servers`**~~ — ✅ 已落地，`engine.run()` 在
   `_discover_microservices()` 后上调为 `max(5, len(service_route_map))`。
3. **结构化指标** — 沙盒启停次数、复用率、平均空闲时长等暴露给 Prometheus。
4. **断点续传** — `processing/` 中残留任务在崩溃重启后自动复活。
5. **细粒度锁 → 读写锁** — 当前 `_dict_lock` 仍然是互斥锁，读热路径下可考虑读写分离
   或无锁结构（参考 `concurrent.futures` 风格）。
