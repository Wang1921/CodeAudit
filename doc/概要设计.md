# 概要设计文档：双轨制多智能体代码审计系统
**版本**: V6.1  |  **状态**: 正式 (Final)

> 变更说明（V6.0 → V6.1）：原 Coordinator 节点已下线 —— 项目测绘与路由提取改由 Semgrep 规则直出，引擎使用 `_discover_microservices()` 直接发现微服务。下文 Agent 名册、消息类型、工作流均已按当前实现修订。

## 1. 系统概述 (System Overview)
传统的静态应用安全测试 (SAST) 工具在面对复杂的代码库时，常面临高误报率、跨文件调用链断裂以及无法发现业务逻辑漏洞的痛点。

本系统旨在构建一个**高度自动化、具备专家级推理能力**的代码审计引擎。通过集成 `opencode` CLI 环境，结合 **A2A (Agent-to-Agent) 协议理念**，利用多个具有特定安全专业领域的大模型智能体 (Agents) 进行协同作战。系统采用独特的**双轨制（自底向上与自顶向下并行）**架构，实现对技术型漏洞（如注入、路径遍历）和业务逻辑漏洞（如越权、条件竞争）的全面覆盖。

## 2. 核心架构理念 (Core Architectural Principles)

### 2.1 双轨并行审查 (Dual-Track Auditing)
+ **技术轨道 (Bottom-Up)**: 通过 Semgrep 静态扫描器发现底层危险函数 (Sinks)，向上逆向追踪，专攻 CWE-22（路径遍历）、CWE-73（文件外部控制）及各类注入漏洞。
+ **业务轨道 (Top-Down)**: 从 API 路由入口向下正向推演，专攻 IDOR（越权）、并发等状态机逻辑漏洞。

### 2.2 文件系统即总线 (A2A over File System IPC)
+ 采用本地文件系统目录（`.a2a_bus/`）作为异步消息总线。
+ Agent 之间通过读写强类型的 JSON 信封 (TaskRequest / TaskResult) 进行任务流转，具备极强的可观测性和容错性。

### 2.3 HTTP 沙盒池管理 (HTTP Sandbox Pool)
+ Python 引擎管理多个 OpenCode 服务器实例，按 cwd 缓存 + LRU 淘汰；默认 5 个并发，引擎启动时按微服务数自动上调至 `max(5, 服务数)`。
+ 细粒度锁：`_dict_lock` 护字典 + per-cwd `_startup_locks` 护冷启动；subprocess 启动 / 健康检查 / dispose 全部在锁外，不同微服务可真正并行启动。
+ 自动健康检查 (`/global/health`)，失败时 dispose 并重启。
+ 双回收策略：容量满时按 LRU 淘汰，主循环空闲时按 Session idle 时长回收（默认 60 秒）。

### 2.4 基于 OpenCode 沙盒的无头执行 ( (Headless Execution)
+ 系统不预先硬编码静态分析工具集。
+ 每个 Agent 作为一个独立的 `opencode` CLI 进程拉起（工作目录挂载为源码根目录），通过大模型自主调用 LSP 进行动态的代码片段提取与跳转。

### 2.5 红蓝对抗验证 (Adversarial Validation)
+ 摒弃单一的漏洞判定器。引入具备"黑客思维"的红队智能体负责构造 Payload 和绕过思路；引入具备"防御思维"的蓝队智能体负责审查代码库中的过滤器、拦截器或业务后置熔断机制，通过左右互搏，系统能最大程度消除传统 SAST 工具的**高误报率**。

### 2.6 控制面与数据面分离 (Control Plane vs Data Plane)
+ **数据面 (Agents)**: 智能体作为无状态的计算节点运行，不写 `.a2a_bus/`。所有分析结果以 JSON 形式通过 **OpenCode HTTP 响应**返回。
+ **控制面 (Python 引擎)**: 唯一写 `.a2a_bus` 的组件。优先读取 OpenCode 服务端 JSON Schema 校验通过的 `structured_output`；无该字段时降级从 `response` 文本提取 JSON；最终由引擎按路由规则写入下一跳信封。
+ **契约强度**：每个 Agent 的 `output_schema` 在 YAML 里声明，通过 `format={type:json_schema}` 传给 OpenCode server 做**服务端强校验**，超过启发式文本解析一个数量级。

### 2.7 工具白名单 (Tool Whitelist)
+ 摒弃 Docker 等重型虚拟化。沙盒边界以 OpenCode 的工具白名单作为主要限制。
+ **统一工具权限**: 当前所有 Agent 拥有 `lsp, read, codesearch` 权限，不赋予 `write`、`bash` 等副作用工具。借助 LSP 实现跨文件代码跳转。
+ **注意**: 引擎并未把源码目录挂为只读（无 bind-mount ro），安全性依赖 OpenCode 对工具白名单的执行。若部署到高敏感环境，建议额外加 `chmod -R a-w` 或容器化挂载。

### 2.8 动态 Prompt 模板加载 (Dynamic Prompt Templates)
+ 所有智能体 Prompt 存储于 `prompts/core/` 目录下的 YAML 文件中，同一文件同时携带 `system_prompt_template` 与 `output_schema`。
+ 引擎通过 `prompts.py` 按 Agent 名静态加载模板，派发时只做 `{payload_json}` 一处变量替换；`output_schema` 在 `agent.execute` 里注入 OpenCode server 做结构化输出校验。

### 2.9 Semgrep 静态扫描集成 (Semgrep Integration)
+ 支持自定义 Semgrep 规则目录或单文件规则（项目内置规则始终包含）。
+ 自动将 Semgrep 输出转换为标准的 `sink_details` 和 `route_details` 格式。
+ 引擎启动时立即触发扫描，对结果按类别分流派发：
  + 每条 API 路由 → LogicAuditor 任务；
  + 每个 `taint_required: true` 的漏洞点 → ReverseTracer 任务（完整污点链）；
  + 每个 `taint_required: false` 的漏洞点 → **BlueValidator fast path**（静态定性，跳过反向追踪与红队），
    适用于弱加密、不安全随机数、硬编码凭证等"sink 即漏洞"的场景。

### 2.10 跨微服务追踪 (Cross-Service Tracing)
+ 自动识别项目中的微服务结构（通过 `pom.xml`, `package.json` 等构建文件）。
+ 支持 ReverseTracer 发出跨微服务追踪请求，引擎自动在所有微服务中并发启动溯源 Agent。
+ 构建全局服务路由表，支持跨服务调用链追踪。

## 3. 动态泛化与安全底线保障 (Generalization & Security Baseline)

### 3.1 规则即追踪策略 (Rules as Tracing Profiles)
+ 面对 Spring/Nginx/Lua 等异构架构，由 `semgrep_rules/custom/` 下的自定义规则承担"路由识别 / 危险点定位"职责，规则升级即可适配新栈。
+ ReverseTracer / LogicAuditor 的提示词通过 `prompts/core/*.yaml` 维护，引擎在派发时注入 Semgrep 输出的 `sink_details` / `route_details`。

### 3.2 引擎级强制安全红线 (Engine-Level Mandatory Overrides)
+ 调度引擎在任务裂变阶段强制干预，不完全依赖 AI 的自觉性。
+ **Semgrep 扫描**: 引擎启动时立即触发 Semgrep 扫描，一次性获取 API 路由和漏洞点。
+ **任务裂变**: 根据扫描结果自动分流——每个路由 → LogicAuditor；每个漏洞点按规则元数据 `taint_required` 分流：`true` → ReverseTracer（完整污点链），`false` → BlueValidator（fast path 静态定性）。
+ **100% 覆盖**: 确保所有 API 路由和危险点都被审计，无遗漏。

## 4. 智能体角色定义 (Agent Roster)
系统由 1 个外部静态扫描器与 5 个 LLM 专家节点组成（验证层拆分为红蓝双角色）；JSON 修复由 `OpenCodeAgent._retry` 内置模板就地完成，不作为独立 Agent 计入。

| 角色名称 | 类型 | 职责说明 | 工具权限 |
| :--- | :--- | :--- | :--- |
| **SemgrepScanner** | 静态扫描器 | 使用内置 + 用户规则扫描代码库，一次性产出 API 路由（`routes`）和危险函数（`sinks`） | 无（外部进程）|
| **ReverseTracer** | 专家节点 | 接收 Sink 坐标，自底向上逆向追踪调用链，支持跨微服务追踪 | `lsp, read, codesearch` |
| **LogicAuditor** | 专家节点 | 从 API 路由向下正向推演业务逻辑漏洞（IDOR、条件竞争等）| `lsp, read, codesearch` |
| **RedValidator** | 攻击验证节点 | 扮演红队构造 Payload，验证漏洞可利用性，生成攻击向量 | `lsp, read, codesearch` |
| **BlueValidator** | 防御验证节点 | 双职责：①扮演蓝队核查防御机制（过滤器、拦截器），确认最终漏洞；②对 `taint_required:false` 的 sink 走 fast path 做静态定性（弱加密 / 弱随机 / 硬编码），跳过 ReverseTracer 与 RedValidator | `lsp, read, codesearch` |
| **ReportGenerator** | 报告节点 | 生成最终审计报告，保存 JSON 格式漏洞报告到 `reports/` 目录 | `lsp, read, codesearch` |

## 5. 通信与协同协议 (A2A Communication Protocol)
系统在项目根目录维护 `.a2a_bus/` 目录群作为交互中枢。所有 Agent 必须遵守严格的 JSON Schema 契约。

### 5.1 目录拓扑
+ `.a2a_bus/pending/`: 待处理任务队列。
+ `.a2a_bus/processing/`: 正在处理的任务。
+ `.a2a_bus/completed/`: 已完成任务与审查结果。
+ `.a2a_bus/failed/`: 契约破坏/执行异常的死信队列。
+ `.a2a_bus/help_req/`: 高优先级跨节点求助队列。

### 5.2 消息类型
+ `TaskRequest`: 任务请求（Semgrep 派发的 LogicAuditor / ReverseTracer 任务）
+ `VulnCandidate`: 疑似漏洞候选（ReverseTracer / LogicAuditor → RedValidator）
+ `ExploitAttempt`: 攻击尝试（RedValidator → BlueValidator）
+ `ConfirmedVuln`: 确认的漏洞（BlueValidator → ReportGenerator）
+ `CrossServiceTraceRequest`: 跨微服务追踪请求（ReverseTracer → 引擎主循环）

## 6. 核心工作流 (System Workflow)
1. **阶段一：初始化 (Initialization)**
    - 引擎调用 `_discover_microservices()` 扫描目标目录第一层子目录，构建 `service_route_map`。
    - 立即触发 `SemgrepScanner.scan()`（合并内置 + 用户自定义规则）。

2. **阶段二：双轨执行 (Execution)**
    - `SemgrepScanner` 返回 `routes` 与 `sinks` 两类结构化结果；入口按 `(vuln_class, filepath, line)` 去重。
    - 引擎根据扫描结果并发派发任务：
      - 为每个 API 路由生成 `LogicAuditor` 任务（`task_id=*_ROUTE_i`）。
      - 为每个 `taint_required:true` 的漏洞点生成 `ReverseTracer` 任务（`task_id=*_SINK_i_TRACE`）。
      - 为每个 `taint_required:false` 的漏洞点生成 `BlueValidator` fast-path 任务（`task_id=*_SINK_i_STATIC`）。

3. **阶段三：动态协同 (Orchestration)**
    - Python 事件循环持续轮询 `.a2a_bus`，按沙盒池调度任务。
    - ReverseTracer 支持跨微服务追踪，可发出 `CrossServiceTraceRequest`，由引擎在所有微服务沙盒中并发拉起接力 ReverseTracer，结果通过 `gather` 收敛。

4. **阶段四：红蓝对抗验证 (Adversarial Validation)**
    - **4.1 攻击推演 (Red Team)**：所有来自双轨执行层的 `VulnCandidate` 首先进入 `RedValidator`。红队节点不看防御，只专注"如果我要利用这个点，应该怎么构造恶意输入？" 如果连红队都觉得无法利用（如参数完全不可控），则直接丢弃；若可利用，则生成附带 Payload 思路的 `ExploitAttempt` 提交给蓝队。
    - **4.2 防御核查 (Blue Team)**：`BlueValidator` 的输入分两类：
      - 路径 A（来自 RedValidator 的 `ExploitAttempt`）：质问"现有的 `SecurityFilter` 或 `XssSanitizer` 能否拦截红队的这个 Payload？" 能拦截 → 误报；防御被击穿 → 正式盖章为真实漏洞。
      - 路径 B（fast path，来自 SemgrepScanner 直发的 `sink_details`）：读 sink 周围上下文做静态定性，判断该静态配置漏洞是否在生产逻辑中生效（排除测试代码 / 示例值 / 已被覆盖的值）；输出仍用 `VULNERABLE/DEFENDED` 双分支，直接进入 ReportGenerator。

5. **阶段五：报告输出 (Reporting)**
    - 引擎汇总 `Validator` 输出的有效 JSON 数据，生成标准化、包含完整调用栈的 JSON 安全审计报告。

## 7. 技术选型与依赖 (Technology Stack)
+ **中枢调度层**: Python 3.10+ (使用 `asyncio` 异步非阻塞模型)。
+ **计算执行层**: `opencode` CLI 环境 (提供 LSP 探针、沙盒执行、大模型上下文管理)。
+ **数据契约层**: JSON (严格的数据模式校验，确保 LLM 输出的结构化与工程鲁棒性)。
+ **静态扫描工具**: Semgrep (用于扫描 API 路由和漏洞点）。

## 8. Web 实时看板 (Real-time Web Dashboard)
+ 内置 HTTP 服务器（端口 8080），提供 Vue.js 驱动的实时监控看板。
+ 显示审计进度、Token 消耗、漏洞统计、Agent 状态、红蓝对抗看板。
+ 支持查看每个 Agent 的会话详情、消息历史、工具调用记录。
